Agent Framework / Preference Discovery

线索猎人 Agent 如何在对话中理解用户偏好

这是一份面向后端落地的补充设计：用户主动表达信号，Agent 只做必要澄清，把自然对话沉淀为可验证、可修改、可追溯的 Lead Preference。

显式信号优先一次只问一个问题用户可纠正不做隐性操纵

01 / PRINCIPLE

目标与边界

目标不是让 Agent 猜中用户的“真实心理”，而是把用户已经主动说出的需求逐步补全为后续动作可使用的结构化信息。

用户主动表达 ↓ 显式偏好识别 → 信息完整？ ── 是 ──→ 写入 Preference Memory ↓ 否 ↓ 选择一个最小澄清问题 ← 用户回答/纠正 ← 继续自然对话 ↓ 更新 Lead / Context / Trace
允许做

抽取原话、识别缺失维度、追问一个关键缺口、复述确认、记录变化。

禁止做

从停留、语气、沉默、点击等行为暗推偏好；用户未提及前主动植入品牌或车型。

02 / SIGNAL MODEL

偏好信号模型

一个“用户喜欢 SUV”还不足以支撑行动。系统要区分用户说了什么、是否确认、为什么重要，以及它会影响哪个决策。

字段说明示例
dimension偏好维度预算、空间、动力、品牌、使用场景、购买时间
value标准化后的值预算 20–25 万；后排空间优先
source_quote用户原话“我经常带父母出门，后排不能太挤”
status确认状态tentative / confirmed / rejected
importance用户是否明确表示优先级must / prefer / neutral
evidence消息、时间、Trace 关联message_id、conversation_id、agent_run_id

  "dimension": "space",
  "value": { "seat_row": "rear", "priority": "must" },

  "status": "confirmed",
  "confidence": 0.96,

}

03 / TIMING

何时进入偏好识别

偏好识别不是每条消息都触发。Runtime 先判断当前对话阶段，再决定是否值得打断对话做澄清。

触发条件

用户明确表达喜欢、在意、排斥、比较、预算、场景或购买限制。

暂不追问

用户正在表达情绪、提出事实问题、回复很短，或当前已有更紧急的登录、权限、人工接管事件。

追问优先级

先补会改变下一步动作的缺口，再补丰富画像但不影响当前动作的细节。

节流规则

同一轮最多一个问题；连续两轮未回答则停止追问，等待用户自然带出新信号。

04 / CLARIFY

轻量追问策略

追问的目的不是扩大销售话术，而是消除一个具体歧义。每个问题都必须能回答“这个答案会改变什么”。

问题模板：复述用户原意 + 指出一个缺口 + 给出低负担选项 + 允许跳过。
用户：我更在意空间。

Agent：你说的“空间”主要是后排乘坐更宽敞，还是后备厢装载更大？
      如果现在不方便细分，也可以先按“都重要”记录。
用户主动信号缺口合适追问
“预算大概 20 万左右。”上限还是舒适区“20 万是总预算上限，还是希望尽量控制在这个区间？”
“主要上下班开。”是否存在周末/长途场景“除了通勤，周末会经常跑高速或带家人出行吗？”
“不想要太费油的。”油耗是硬约束还是偏好“低油耗是必须满足，还是在动力相近时优先考虑？”

05 / MEMORY

Preference Memory 与状态

偏好写入 Lead Memory 前必须区分“暂定理解”和“用户确认”。用户的新表述可以覆盖旧值，但旧值不能被静默抹除。

TENTATIVE → CONFIRMED ↘ ↙ REJECTED → ARCHIVED 同一维度的新信号： 旧值保留为历史 → 新值建立证据 → Context Builder 只读取当前有效值
  • 用户直接表达且语义明确：可以直接写入 confirmed。
  • 用户表达含糊或 Agent 做了标准化：先写 tentative，由下一轮确认。
  • 用户说“不是这个意思”：当前值标记 rejected，保存纠正原话。
  • 偏好发生变化：创建新版本，不覆盖历史 Trace。
  • 推荐或触达前：Policy 检查是否存在冲突、过期或未确认的关键约束。

06 / RESPONSIBILITY

Agent、Skill、Runtime 怎么分工

组件职责不负责什么
线索猎人子 Agent理解用户原话，决定是否需要澄清和如何自然表达。不直接修改状态机，不绕过 Policy。
Preference Skill抽取偏好、识别缺口、生成结构化候选和澄清问题。不发送私信、不调用真实 RPA。
Skill Runtime调度 Skill，管理超时、重试、预算、版本和 Trace。不替 Agent 决定用户喜欢什么。
Context Builder把当前有效偏好、Lead Memory 和最近对话组装给 Agent。不把历史猜测当成事实。
Policy / Permission决定是否可以推荐、触达、升级人工或写入敏感字段。不生成对话内容。

07 / EXAMPLES

完整对话示例

示例 A：自然补全空间需求

用户：我经常带父母出门，所以空间要舒服一点。
Agent：明白，你更关注乘坐舒适度。主要是后排腿部空间，还是上下车方便？
用户：后排腿部空间，老人坐着不能憋屈。
系统：写入 space.rear_legroom = must，状态 confirmed。
Agent：收到，我会优先按后排腿部空间筛选，后面再结合预算和动力看方案。

示例 B：用户拒绝补充

用户：我先看看，预算还没想好。
Agent：没问题，我先不记录预算。你更想先了解空间、动力，还是日常使用成本？
用户：先看空间吧。
系统：不创建预算偏好；将 conversation_focus 设为 space。

示例 C：用户纠正 Agent

用户：我说省油，不代表我不要动力。
系统：将“低油耗 = must”标记 rejected，保留原证据。
Agent：明白，你是希望在动力够用的前提下尽量省油，我按这个条件理解。

08 / ACCEPTANCE

验收标准与指标

上线前底线：不能只验收“Agent 问得像不像人”，还要验收偏好是否有证据、能否纠正、是否被正确消费。
  • 用户未主动表达时，不产生新的偏好事实。
  • 每次追问最多一个问题，连续两轮未回应后自动停止。
  • 每条 confirmed 偏好都能追溯到 source_quote 和 message_id。
  • 用户否定或修改后，旧偏好不再被 Context Builder 当作当前值。
  • 推荐、触达和人工交接前，能读取当前有效偏好并记录消费 Trace。
  • 发生 LLM Invalid Output 时，按既有 Retry 规则重试，不能写入半结构化结果。
理解质量

显式偏好抽取准确率、澄清后确认率、用户纠正率。

对话负担

平均澄清轮数、连续追问中断率、用户跳过率。

业务可用性

偏好被推荐/触达正确消费的比例、人工交接信息完整率。

治理质量

无证据偏好写入数、被 Policy 阻断数、Trace 完整率。
