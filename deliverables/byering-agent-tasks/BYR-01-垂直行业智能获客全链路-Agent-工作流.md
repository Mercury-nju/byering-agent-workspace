# 任务一：垂直行业从找人到触达的完整获客 Agent

## 01 任务基本信息

| 字段 | 内容 |
|---|---|
| 任务名称 / ID | BYR-01 - 针对垂直行业的从找人、分析到触达的获客 Agent |
| 所属行业 / 职能 | 学生自选一个适合公开内容获客的垂直行业，例如汽车、医美、家装、职业教育、企业服务、本地生活或其他细分领域 |
| 业务 Owner / 使用角色 | 该行业的销售主管、获客负责人 |
| 触发方式 / 使用频率 / 任务量 | 绑定账号后长期执行，从用户账号自己的作品内容、互动和直播弹幕中筛选出30条高意向的潜客  |
| 当前最希望改善什么 | 将该行业中“人工找人、判断需求、准备并执行首次触达、记录结果”的重复工作串成由 主 Agent 协调、子agent执行的可复查工作流 |

## 02 最小任务闭环

请先自行选择一个垂直行业，并说明为什么该行业存在可通过公开内容、评论、互动或直播间发现的获客机会。随后自行设定一个明确业务目标，例如“为某新能源汽车门店发现高意向试驾咨询线索””。

当该行业的业务 Owner 提出获客目标时，Byering 主 Agent 接收目标，确认任务；随后组织专业子 Agent ：找人、找到人之后分析判断意向、生成对应内容，私信发送，完成触达，最后监听私信后续消息，判断用户是否留资，即完整线索转化。

- 本次只解决的一个小需求：完成“找人 → 判断 → 准备内容 → 发送私信 → 监听回复 → 留资或转人工 → 记录结果”的最小获客闭环。
- 当前耗时 / 等待时间 / 返工情况：人工通常需要在多个内容页面和评论中反复筛选；同一用户可能多次出现，且“求推荐”“想了解”“只围观”容易被混淆。
- 任务完成后，结果被谁、在什么系统或流程中继续使用：获客负责人在该 Agent 的结果中心查看潜客清单、发送记录、用户回复和留资/转人工结果；销售据此继续跟进或导出名单自行处理。

## 03 当前 AI / Agent / Skill 链路

| 环节 | 当前使用的能力 | 实际情况 |
|---|---|---|
| 输入 / 上下文 | 用户、企业已授权绑定的抖音账号信息、该账号发布的作品、作品评论、直播弹幕、已有私信会话、自行上传的企业知识库、企业服务信息和销售规则等 | 只找用户自己账号下的潜客、用户信息，禁止在公域如其他账号的评论区、直播间找潜客触达。 |
| 模型 / Agent / Skill | 自研主 Agent +子agent协同产品框架；学生自行设计“找人、分析、触达”三项核心能力如何拆成一个主agent或+多个子 Agent的协同模式 | 不严格限制子 Agent 数量必须为3个，可以细拆，但必须说明每个能力由谁完成、拿到什么输入、交付什么结果、失败后谁处理 |
| 工具 / 数据接入 | 抖音账号授权登录到云电脑环境执行，通过rpa的能力进行内容/评论/直播互动读取、私信读取和发送、线索记录、规则检查等执行动作 | 可使用自己账号或经过授权的测试账号；必须能展示内容读取、分析、发送、失败的全过程 |
| 输出 / 人工接管 | 潜客清单、意向判断、私信内容、发送记录、用户回复、留资结果、转人工记录 | 用户明确拒绝、投诉、敏感信息、价格承诺、要求真人或 Agent 无法判断时，必须停止自动处理并交人工 |

- 学生需要自行解释：找人能力如何从作品评论、直播弹幕、关注/互动或私信入口中发现潜客；分析能力如何判断意向；触达能力如何决定说什么、何时发、何时停。
- 可以先用规则完成明确部分，再用模型处理语义判断；但不能把模型输出直接当成事实或发送指令。
- 所有发送、重试、人工接管和留资结果都需要留下可回看的记录。

## 04 当前做法与失败模式

| 步骤 | 人 / AI / Agent 在做什么 | 判断或交接点 |
|---:|---|---|
| 1 | 用户授权登录绑定抖音账号，默认长期执行获客任务。  | 运营需要先确认：想找什么样的人、什么情况才算有效线索；信息不清时容易靠猜或反复询问主 |
| 2 | 找人能力持续读取企业账号自己的作品评论、直播弹幕、互动和私信入口，找出可能有需求的人 | 同一用户在多个入口出现时必须合并，不能重复算作多个潜客 |
| 3 | 分析能力判断用户是否有需求、处于什么阶段、是否值得联系，以及依据是什么 | 不明确时不计入潜客名单，不能编造预算、地域或购买能力，给出如待确认这样的模棱两可的标签用户 |
| 4 | 触达能力为可联系用户生成首条私信，检查重复联系、拒绝记录和不应承诺的内容，再发送消息 | 发送失败、风险命中或用户明确拒绝时立即停止 |
| 5 | 私信承接能力监听用户后续回复，判断继续回答、追问、预约、收集联系方式、转人工或结束对话 | 用户留资后创建线索记录并通知销售；用户要求真人、投诉或出现敏感信息时转人工 |

- 最常见的失败模式：漏掉直播间中的高意向发言；把围观或夸赞误判为购买意向；同一用户在评论和私信中被重复联系；模型编造价格、效果或库存；发送失败却显示成功；用户明确拒绝后仍继续联系；人工接管后 Agent 仍在回复。
- 出错后如何发现、谁来处理、平均需要多久：通过账号内的来源记录、用户 ID、消息记录、发送结果和人工抽检发现；规则类问题直接阻断，判断不清、投诉或高风险情况立刻交给人工销售/运营处理。
- 哪些情况必须停止自动处理并转人工：用户明确拒绝、投诉、未成年人或敏感信息、索要价格/效果/合同承诺、要求真人、准备留资但信息不完整、发送服务报错、账号登录失效或任何未授权操作。

## 05 输入、输出与样例

- 输入来源、格式、关键字段、权限要求：选择一个企业/个人账号场景，提供该账号的至少 5 条作品或直播片段，以及从其中产生的评论、弹幕、互动或私信测试材料。材料应覆盖“有明确需求、只是围观、明确拒绝、重复出现、需要人工处理”五种情况。可使用测试账号和经授权的测试会话。
- 输出格式、使用人、下游系统或动作：输出一份“获客结果中心”，清楚展示：从哪里找到这个人、他为什么可能有需求、是否已联系、发了什么、对方怎么回复、是否已留资。由企业销售主管或运营负责人使用。
- 可提供的样例数量：至少处理 30 条来自评论、直播或私信的互动信息；整理出至少 10 位潜客；至少完成 1 段测试私信会话，展示能够承接私信对话的能力。
- 可提供的复现材料：账号授权或测试账号说明、互动信息样例、筛选规则、发送记录、用户回复记录、留资/转人工记录，以及一次失败后如何恢复或停止的记录。

## 06 验收与 Benchmark 线索

- **合格标准**：1) 每个潜客都能回到企业账号内的评论、直播、互动或私信来源；2) 同一用户不会重复联系；3) 找人、分析、发送、回复、留资或转人工的状态能连续记录；4) 用户明确拒绝、发送失败和人工接管时，Agent 会正确停止或转交。
- **不可接受的错误 / 红线**：伪造来源、发送结果或用户回复；把猜测当成用户事实；绕过企业授权使用账号；对明确拒绝的用户继续联系；对投诉、敏感信息或人工接管会话继续自动回复。
- **核心评测维度**：从企业自身内容中找人是否有效、意向判断是否可靠、触达是否贴合用户、私信承接是否自然、留资判断是否准确、状态记录是否完整、风险时是否及时交人工。
- **当前已有评测方式或测试集**：候选人需提供覆盖评论、直播、私信三类来源的材料，并至少包含高意向、低意向、拒绝、重复、投诉/敏感和人工接管案例。
- **如果只优化一件事，什么结果会让你认为能力明显变好？**：让企业能清楚看到一条线索从哪来、Agent 做了什么、为什么这样做，以及最终是否真正转化为可跟进的销售线索。

## 07 第一版落地范围

- 希望看到的第一版成果：绑定一个账号后，Agent 能持续从该账号的内容、评论、直播和私信中找人，完成分析、触达、私信承接和留资/转人工判断，并在结果中心留下完整过程。
- 本次包含：账号授权、内容互动读取、找人、线索合并、意向分析、私信生成与发送、回复监听、留资判断、结果记录和异常处理。
- 本次暂不包含：生产 CRM 深度集成、大规模无差别群发、自动签约/收款、没有人工边界的长期无人值守。
- 必须保留的人工确认点：账号授权、企业目标与触达规则设置、价格/优惠/合同承诺、投诉和敏感问题、人工接管后的后续处理。
- 期望验证周期 / 反馈人 / 反馈频率：5-10 天；由 Byering 产品/业务负责人在首轮交付后统一反馈一次。

## 08 数据与使用边界

- 数据处理方式：授权账号自身产生的内容互动、直播互动和私信；演示时可使用测试账号和经授权测试会话。
- 不可提供或不可接入的内容：未授权账号密码/Cookie、企业外部系统、与获客无关的客户隐私、支付信息和非必要的完整联系方式。
- 权限、审计、留痕、删除周期等要求：账号授权状态必须可见；每条线索必须保留来源；每次私信发送、用户回复、留资和人工接管必须有时间记录；用户明确拒绝后不再继续联系；测试数据按企业要求删除。
- 使用范围：人才筛选、产品共创和内部试点演示。
