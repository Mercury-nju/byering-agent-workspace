# 任务三：抖音互动找客户 Agent

## 01 任务基本信息

| 字段 | 内容 |
|---|---|
| 任务名称 / ID | BYR-03 - 抖音互动找客户 Agent |
| 所属行业 / 职能 | 抖音内容获客 / 内容运营 |
| 业务 Owner / 使用角色 | 获客负责人、内容运营或销售主管 |
| 触发方式 / 使用频率 / 任务量 | 企业授权并绑定自己的抖音账号后长期运行；当作品评论、直播弹幕或互动关注信息新增时处理 |
| 当前最希望改善什么 | 从大量互动信息里稳定找出真正可能有需求的人，避免运营人员逐条翻看，也避免把围观互动误认为客户 |

## 02 最小任务闭环

请自行选择一个适合通过抖音内容获客的行业，并说明什么样的评论、直播发言或互动关注可以反映用户可能有需求。例如，汽车行业中询问车型、试驾、落地价或置换的互动；职业教育中询问课程、报名、学习周期或就业的互动。

当企业账号出现新的评论、直播弹幕或互动关注信息时，Agent 读取相关内容，结合企业提供的目标客户描述，自动找出意向度高的客户，并为每一位用户留下原话或互动证据、来源和判断理由。

- 本次只解决的一个小需求：从企业自己账号的评论、直播弹幕和互动关注信息中，自动找出意向度高的客户。
- 当前耗时 / 等待时间 / 返工情况：运营人员需逐条翻评论、直播互动和关注通知，既容易漏掉咨询型发言，也容易把“好看”“求同款”“哈哈哈”或单纯关注误判为客户需求。
- 任务完成后，结果被谁、在什么系统或流程中继续使用：获客负责人查看互动潜客名单，确认后可交给任务二的私信触达 Agent 或人工销售跟进。

## 03 当前 AI / Agent / Skill 链路

| 环节 | 当前使用的能力 | 实际情况 |
|---|---|---|
| 输入 / 上下文 | 企业已授权绑定的抖音账号、该账号的作品评论、直播弹幕、互动关注信息、企业服务介绍、目标客户描述和筛选规则 | 只读取企业自己账号内的互动，不读取私信，不进入其他账号找人 |
| 模型 / Agent / Skill | AI模型+RPA爬虫识别需求信号、排除无关互动、合并同一用户的多次出现，并说明判断依据 | 可以使用规则和模型配合；不能把猜测写成用户事实，也不能只因一个关键词、点赞或关注就判为客户 |
| 工具 / 数据接入 | 抖音账号授权登录到云电脑环境，通过 RPA 读取作品评论、直播弹幕和互动关注信息；线索记录工具 | 可使用自己账号或经过授权的测试账号；需实际展示互动读取和结果整理过程 |
| 输出 / 人工接管 | 互动潜客名单：用户、来源、原话或互动证据、需求判断、判断理由和待确认项 | 用户明确拒绝、投诉、互动含敏感信息或需求判断不清时，不进入自动跟进名单，交人工确认 |

- 学生需要先定义：哪些评论、直播发言或互动关注是有效需求信号，哪些只能算围观、夸赞、玩笑或信息不足。
- 同一用户在评论、直播或互动关注中多次出现时，应合并为一条潜客记录，并保留全部来源。
- 本题不发送私信、不处理私信回复；只完成互动找客户。

## 04 当前做法与失败模式

| 步骤 | 人 / AI / Agent 在做什么 | 判断或交接点 |
|---:|---|---|
| 1 | 用户授权登录抖音账号，rpa自动监听作品评论、直播场次和互动 | 先确定范围，避免漏看或把旧互动重复处理 |
| 2 | rpa从评论、直播弹幕和互动关注中挖掘信息，大语言模型识别用户是否在询问产品、服务、价格、预约、适用场景或购买条件 | 夸赞、表情、玩笑、单纯关注和无关内容不进入潜客名单；信息不足时标记“待确认” |
| 3 | 查看同一用户是否在不同来源重复出现，并汇总其有效信息 | 同一用户只形成一条潜客记录，不能因多次互动重复计入 |
| 4 | 将有价值的互动和用户整理给获客负责人 | 用户明确拒绝、投诉、敏感信息或判断不清时，停止自动判断并交人工 |

- 最常见的失败模式：把“求链接”、单纯夸赞或关注当成强需求；漏掉表达较含蓄的咨询；同一用户重复入库；模型编造预算、地域或购买能力；潜客记录找不到原始互动。
- 出错后如何发现、谁来处理、平均需要多久：负责人应能从每条潜客记录直接回到原作品、原评论、原直播弹幕或互动通知核查；规则问题由系统拦截，判断不清或有争议的互动交运营负责人处理。
- 哪些情况必须停止自动处理并转人工：用户明确拒绝、投诉、未成年人或敏感信息、互动语义无法确认但疑似高价值、账号读取异常或任何未授权操作。

## 05 输入、输出与样例

- 输入来源、格式、关键字段、权限要求：选择一个企业或个人测试账号，提供至少 5 条作品或直播片段，并从中实际读取不少于 30 条评论、直播弹幕或互动关注信息。材料需覆盖明确需求、围观无关、重复出现、明确拒绝和需要人工确认五种情况。
- 输出格式、使用人、下游系统或动作：输出一份“互动潜客名单”，每条至少展示用户、来源、原话或互动证据、是否值得跟进、判断理由和待确认项；由获客负责人决定是否交给任务二或人工跟进。
- 可提供的样例数量：至少处理 30 条互动信息；整理出至少 10 位潜在客户；其中应包含值得跟进、不值得跟进和待人工确认三类结果。
- 可提供的复现材料：账号授权或测试账号说明、指定作品或直播、实际读取的互动信息、筛选规则、互动潜客名单和至少 3 条边界案例的处理说明。

## 06 验收与 Benchmark 线索

- **合格标准**：1) 每位潜客都能回到企业账号内的具体评论、直播弹幕或互动关注来源；2) 同一用户不会重复进入潜客名单；3) 围观、无关、明确拒绝和判断不清的互动不会被当成高意向客户。
- **不可接受的错误 / 红线**：伪造互动来源；把猜测当成用户事实；读取企业自己账号以外的互动；编造预算、地域、购买能力或联系方式；未经确认发送私信。
- **核心评测维度**：需求互动识别是否有效、判断是否保守、来源是否可回查、同一用户是否合并、边界情况是否处理清楚。
- **当前已有评测方式或测试集**：候选人需提供明确需求、低意向/无关、重复、拒绝和信息不足的完整互动样例。
- **如果只优化一件事，什么结果会让你认为能力明显变好？**：运营负责人不用重新翻完整评论、直播和互动记录，也能迅速确认“这个用户为什么值得联系”。

## 07 第一版落地范围

- 希望看到的第一版成果：绑定一个测试账号后，Agent 能读取该账号的评论、直播弹幕和互动关注信息，输出一份来源清楚、可人工复核的互动潜客名单。
- 本次包含：账号授权、作品/直播范围选择、评论/弹幕/互动读取、需求识别、同一用户合并、结果记录和异常处理。
- 本次暂不包含：私信发送、私信回复、自动留资、CRM 写入和大规模无差别触达。
- 必须保留的人工确认点：企业目标客户定义、筛选规则、判断不清的高价值互动、投诉和敏感信息。
- 期望验证周期 / 反馈人 / 反馈频率：1-3 天；由 Byering 产品/业务负责人在首次交付后统一反馈。

## 08 数据与使用边界

- 数据处理方式：仅使用企业已授权账号自身产生的评论、直播弹幕和互动关注信息，以及自己账号或经授权测试账号材料。
- 不可提供或不可接入的内容：未授权账号密码/Cookie、其他账号的互动、私信内容、企业外部系统、支付信息和非必要的完整联系方式。
- 权限、审计、留痕、删除周期等要求：账号授权状态应可见；每条潜客必须保留互动来源、原话或互动证据和判断时间；测试材料按企业要求删除。
- 使用范围：人才筛选、产品共创和内部试点演示。
