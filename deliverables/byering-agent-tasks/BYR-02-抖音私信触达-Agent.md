# 任务二：抖音私信触达 Agent

## 01 任务基本信息

| 字段 | 内容 |
|---|---|
| 任务名称 / ID | BYR-02 - 抖音私信触达 Agent |
| 所属行业 / 职能 | 抖音获客 / 销售运营 |
| 业务 Owner / 使用角色 | 获客负责人、销售运营或私信运营 |
| 触发方式 / 使用频率 / 任务量 | 获客负责人确认一批可联系用户和触达内容后触发；单次处理一批已确认名单 |
| 当前最希望改善什么 | 让“已经决定联系谁、该说什么”后的发送动作真正稳定落地，不再靠人工逐个复制、搜索、发送和记结果。 |

## 02 最小任务闭环

请自行选择一个适合抖音获客的行业，并设定一个清楚的触达目的。例如，汽车门店邀请已咨询试驾的用户补充方便到店的时间；职业教育机构邀请已咨询课程的用户说明当前最关心的问题。

当获客负责人提供一批已经确认可以联系的用户、已确认的私信内容和发送规则后，Agent 使用企业已授权绑定的抖音账号通过该agent发送私信，并检查是否重复联系或命中禁止联系规则，并记录每条消息的实际发送结果。

- 本次只解决的一个小需求：把一份已确认的触达名单，交付给agent稳定真实执行私信发送，并做好用户管理。
- 当前耗时 / 等待时间 / 返工情况：运营人员需要逐个搜索用户、确认没有重复联系、复制内容、发送并手工记录；账号切换、页面变化和发送失败都容易造成漏发、重发或误记成功。
- 任务完成后，结果被谁、在什么系统或流程中继续使用：获客负责人查看逐用户发送结果；已发送用户后续由私信承接 Agent 或人工销售继续跟进。

## 03 当前 AI / Agent / Skill 链路

| 环节 | 当前使用的能力 | 实际情况 |
|---|---|---|
| 输入 / 上下文 | 获客负责人确认的用户名单、每位用户的账号标识、已审核的首条私信内容、发送时间和禁止联系规则 | 名单由上游任务或人工提供； |
| 模型 / Agent / Skill | 学生自行设计“私信触达”能力：确认发送对象和内容，检查重复/拒绝/人工暂停状态/平台疯狂，通过已授权账号完成发送并记录结果 | 可以和agent对话，在不改变目的原意的前提下，替换已批准变量，如触达的花束语气；不得自行编造优惠、价格、效果或其他业务承诺 |
| 工具 / 数据接入 | 抖音账号授权登录到云电脑环境，通过 RPA 打开私信、定位用户、发送消息并读取发送结果；发送记录工具 | 可使用自己账号或经过授权的测试账号；必须展示实际发送过程和平台返回的结果 |
| 输出 / 人工接管 | 逐用户发送记录：发送内容、发送时间、成功/失败/未知状态、失败原因和是否需人工处理 | 用户已拒绝、重复联系、账号不匹配、发送异常或内容超出规则时，必须停止发送并交人工确认 |

- 学生需要说明：如何确保发给正确的人、如何避免重复联系、如何确认消息确实发送成功，以及发送失败后如何处理。如何避免一次性触达大量用户的平台风控。
- 若平台未明确返回成功结果，只能标记为“未知”或“失败”，不能写成已发送。

## 04 当前做法与失败模式

| 步骤 | 人 / AI / Agent 在做什么 | 判断或交接点 |
|---:|---|---|
| 1 | 获客负责人提供可联系用户名单、已审核内容和发送规则 | 名单或内容不完整时不发送，先由负责人补全 |
| 2 | 运营人员在企业账号内逐个定位用户，确认账号身份、历史联系记录和拒绝标记 | 找不到用户、身份不一致、已联系或已拒绝时，不发送并记录原因 |
| 3 | RPA按已批准内容发送私信，并控制发送节奏 | 内容涉及价格、优惠、效果、合同或未批准承诺时，必须暂停并交人工 |
| 4 | 记录平台实际结果并交回获客负责人 | 成功、失败和未知必须分别记录；失败或未知不能盲目重复发送 |

- 最常见的失败模式：把消息发给同名或错误账号；同一用户被重复联系；未检查拒绝记录仍继续发送；页面显示异常却记录为成功；发送失败后盲目重试；发送内容超出企业允许范围。
- 出错后如何发现、谁来处理、平均需要多久：通过每条记录中的用户账号、发送时间、发送内容和平台回执核查；账号身份、内容和规则问题由获客负责人处理，登录或平台异常由操作人员处理。
- 哪些情况必须停止自动处理并转人工：用户明确拒绝、投诉、已有人跟进、名单账号无法确认、内容需要价格/优惠/合同承诺、账号登录失效、平台限制或任何未授权操作。

## 05 输入、输出与样例

- 输入来源、格式、关键字段、权限要求：选择一个企业或个人测试账号；由人工提供至少10 位已确认用户的测试名单、已审核首条私信内容和发送规则。名单中需包含至少一位重复联系、明确拒绝或不应发送的用户。
- 输出格式、使用人、下游系统或动作：输出逐用户发送记录，至少展示用户、原定发送内容、实际发送时间、平台结果、失败/拦截原因和下一步处理人；由获客负责人查看并交给私信承接 Agent 或人工销售。
- 可提供的样例数量：至少处理 5 位测试用户；其中至少 3 位在授权测试账号中实际完成发送；至少 1 位因重复、拒绝或身份无法确认而被正确拦截。
- 可提供的复现材料：账号授权或测试账号说明、测试名单、发送规则、逐用户发送记录和至少 2 条发送失败或拦截案例的处理说明。测试消息不得包含真实客户隐私或真实联系方式。

## 06 验收与 Benchmark 线索

- **合格标准**：1) 每一条消息都只发送给已确认名单中的正确账号；2) 已拒绝、重复联系或身份不清的用户不会被发送；3) 发送记录与平台实际结果一致，成功、失败和未知状态不混淆。
- **不可接受的错误 / 红线**：伪造已发送结果；发送失败后无判断地重复发送；绕过账号授权或平台限制。
- **核心评测维度**：执行稳定性、对象核验、重复/拒绝拦截、发送结果真实性、失败处理和过程留痕。
- **当前已有评测方式或测试集**：候选人需提供正常发送、重复联系、明确拒绝、账号不匹配和发送异常五类测试情况。
- **如果只优化一件事，什么结果会让你认为能力明显变好？**：负责人无需逐条盯着操作，也能确信“该发的发出去了，不该发的一条都没有发错”。

## 07 第一版落地范围

- 希望看到的第一版成果：输入一份已确认测试名单和已审核私信内容后，Agent 能在授权账号内逐条执行发送，并输出真实、可回查的发送记录。
- 本次包含：账号授权、名单读取、账号核验、重复/拒绝检查、私信发送、平台结果读取、失败处理和发送记录。
- 本次暂不包含：从评论或直播中找人、意向分析、私信自动承接、自动留资、CRM 深度集成和大规模无差别群发。
- 必须保留的人工确认点：待发送名单、首条消息内容、价格/优惠/合同承诺、投诉和敏感问题、异常发送后的后续处理。
- 期望验证周期 / 反馈人 / 反馈频率：2-3 天；由 Byering 产品/业务负责人在首次交付后统一反馈。

## 08 数据与使用边界

- 数据处理方式：仅使用企业已授权账号，以及自己账号或经授权测试账号之间的测试名单和测试消息。
- 不可提供或不可接入的内容：未授权账号密码/Cookie、真实客户隐私、支付信息、企业外部系统和非必要的完整联系方式。
- 权限、审计、留痕、删除周期等要求：账号授权状态应可见；每次发送、发送失败、发送未知和人工拦截均需保留时间记录；测试数据按企业要求删除。
- 使用范围：人才筛选、产品共创和内部试点演示。
