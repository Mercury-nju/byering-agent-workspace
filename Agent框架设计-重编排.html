产品目标与总体架构

先理解 Byering、主 Agent、运行时和线索猎人的整体关系。

01一、核心结构：主 Agent + 确定性运行时 + 专业子Agent

主 Agent 负责决策，确定性程序负责执行控制，子 Agent 负责专业工作。

WORKFLOW / CONFIGCODE 001
主 Agent：决定做什么、找谁、如何验收
运行时：控制顺序、权限、预算、状态、重试
子 Agent：调用工具并产生真实结果

优点是可控、可观察、可恢复，也最适合现有办公室、任务房间、资源中心和 Agent 档案系统。

02二、核心原则

现有 RPA Workflow 继续作为核心执行资产。Agent 负责理解、判断、决策和组织，RPA 负责稳定操作真实界面，Python 负责确定性数据处理，LLM 负责语义理解和动态决策，Skill 负责把这些能力统一封装。

04四、现有线索猎人项目背景

当前已有一套基于云电脑、RPA、Python 和大模型运行的抖音获客 Workflow。

现有业务流程如下：

用户通过云电脑授权登录自己的抖音账号

RPA 接管云电脑中的抖音账号

RPA 定时或持续采集账号相关互动信息

采集范围包括：

用户作品评论

新增关注

私信

直播间互动

Python 对原始数据进行清洗、去重、结构化等处理

大模型分析互动内容及用户行为

判断潜在客户的购车意向

将客户划分为高、低意向

对符合触达规则的高意向客户主动发送私信

后续持续监听客户回复

大模型结合客户上下文继续回复

持续推进客户沟通

当客户提供手机号、微信等联系方式后，认为完成留资

生成客户摘要并交付真人销售或后续 CRM

V1.0 的目标，是把现有 Workflow 封装成为一个具备岗位身份、Soul、Memory、Skill、状态、权限和绩效的数字员工。

该数字员工统一命名为：线索猎人

线索猎人核心目标：持续监控抖音账号产生的用户互动，从中识别潜在购车客户，对高价值客户进行主动触达，并通过持续沟通推进客户完成留资。

08八. Skill Domain

How to read this section

Skill Domain 是能力分组，不是 Agent 或独立服务

在本 V1 设计里，Domain 只是把线索猎人的工作按业务阶段归类。真正被 Runtime 调用、记录和重试的是 Skill；Skill 再交给对应的 Executor 执行。因此，一个 Domain 可以包含多个 Skill，但不需要对应一个新的 Agent 或微服务。

Domain回答“这项能力属于哪个业务阶段”。
Skill回答“系统具体要完成什么动作”。
Executor回答“这个动作由什么技术方式执行”。
ACCOUNT→OBSERVE→LEAD→INTENT→OUTREACH→CONVERSATION→CONVERSION
ACCOUNT让账号处于可用状态：连接、检查 Session、恢复 Session。
OBSERVE从抖音持续采集评论、关注、私信和直播互动。
LEAD把外部用户识别成 Lead，并聚合其多种互动信号。
INTENT从文本和行为中提取购车信号，判断意向并计算评分。
OUTREACH检查是否允许主动触达，制定策略、生成消息并发送。
CONVERSATION理解客户回复、更新记忆、决定下一步并生成回复。
CONVERSION判断留资时机，提取手机号或微信，完成 Lead 并生成摘要。
完整例子：“325Li 杭州最近落地多少？”先由 OBSERVE 采集，再由 LEAD 建立身份，INTENT 识别车型、城市和价格咨询，OUTREACH 完成触达，后续由 CONVERSATION 持续沟通，最终由 CONVERSION 提取联系方式并完成留资。

V1 Workflow 说明：它们是 Runtime 调用的执行器

这 7 个 Workflow 不是 7 个 Agent，也不负责意向判断和销售策略。它们只负责在云电脑和抖音页面上完成稳定、可验证的真实操作，并把原始结果交还给 Skill Runtime。下方顺序是能力分组，不代表每次运行都按同一条链路调用。

账号前置→互动采集→事件规范化→Lead / 意向→策略检查→发送或回收
统一约束：所有 Workflow 使用同一请求协议和返回协议；Runtime 负责调度、账号锁、重试、幂等、Trace，Workflow 只返回成功结果或标准错误状态。
