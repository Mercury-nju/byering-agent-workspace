## 1. 一句话说明

**Byering 是面向抖音经营者的 AI 获客与客户转化工作台。**

它不是一个只会聊天或写文案的通用 AI，而是一套把“发现互动用户、判断潜客、执行首次私信、承接后续对话、人工接管、沉淀结果”串成完整业务链路的 Agent 系统。

用户只需要表达想达成的业务结果，例如：

> 帮我把账号里最近出现的高意向互动用户找出来，筛出值得联系的人，并持续接待回复。

Byering 会将目标转成有边界的任务，要求必要的账号授权和确认，调用对应 Agent 执行，并把证据、回执、会话和结果回写到统一的成果中心。

它解决的不是“有没有内容可生成”，而是：

```text
今天哪些人值得跟进？
哪些人已经表达了真实需求？
哪一步可以自动化，哪一步必须由我确认？
实际发出去了吗？客户回复了吗？现在该谁接手？
```

## 2. 产品定位、用户与边界

### 2.1 服务对象

当前产品最适合以下用户：

| 用户类型 | 典型问题 | Byering 的核心价值 |
| --- | --- | --- |
| 抖音小店、商家与品牌主 | 评论、私信、直播互动很多，人工跟不过来 | 将互动信号变成可筛选、可跟进的潜客和会话 |
| 主播与直播运营团队 | 弹幕不断出现，没人能稳定记录需求和后续动作 | 实时分析弹幕，按规则发起或安排后续动作 |
| 内容创作者与个人 IP | 有流量但缺少稳定的转化动作 | 从作品与互动中发现需求，持续承接咨询 |
| 一人公司、专业顾问与小型销售团队 | 没有完整 SDR、运营和客服团队 | 用 Agent 接住重复的找人、分析、触达和初步接待 |
| 需要增长研究的运营人员 | 不知道什么内容和什么人群值得投入 | 分析爆款作品、账号、评论和趋势，给出带证据的判断 |

### 2.2 解决的问题

抖音经营中的线索并不稀缺，稀缺的是把碎片信号转成后续业务动作的能力。用户每天会面对评论询价、直播提问、关注互动、私信咨询、竞品比较和内容反馈，但人工通常无法持续完成下面的闭环：

```text
发现用户
  -> 记录来源
  -> 判断是否值得推进
  -> 联系前确认内容与权限
  -> 真实执行
  -> 等待平台回执
  -> 承接回复
  -> 交给人工成交或继续跟进
```

Byering 的价值是将这条链路变成有状态、有证据、有权限边界的日常业务系统。

### 2.3 不是什么

为了避免误解，Byering 当前不应被描述成以下产品：

- 不是“输入一句话就能无边界自动经营所有平台”的黑箱；
- 不是批量骚扰、绕过平台权限或伪造触达结果的工具；
- 不是把点赞、停留、单个关键词直接判定为购买意向的评分器；
- 不是把“请求已提交”当作“消息已送达”的群发软件；
- 不是一个可让任意 Agent 自行扩大权限、读取任意账号数据的系统；
- 不是用虚构数据填满经营看板的演示应用。

Byering 的设计原则是：**先确认事实、账号和权限，再做动作；先拿到回执，再把结果记为完成。**

## 3. 核心产品承诺

### 3.1 从互动到客户资产

Byering 将抖音中的评论、直播弹幕、互动通知、授权账号私信、账号资料和作品数据，逐步整理为用户可经营的资产：

```text
原始互动用户
  -> 待分析对象
  -> 有证据的潜客
  -> 待触达 / 已触达
  -> 跟进中会话
  -> 已留资 / 成交跟进 / 已转化
```

每个状态都不是一句展示文案，而应有可追溯的来源、时间、任务、账号和证据。

### 3.2 从 Agent 能力到业务结果

用户不需要先理解“什么是爬虫、MCP、提示词或工作流”。产品将能力包装为明确岗位：找人、分析、触达、私信对话和内容研究。

但用户也不会失去控制权。用户始终能：

1. 选择授权哪个抖音账号；
2. 决定业务目标、筛选条件、内容边界和发送额度；
3. 在高风险或外部发送前明确确认；
4. 查看每一步的真实运行状态、证据和回执；
5. 接管私信对话，或恢复 AI 接待；
6. 暂停、恢复、重试或停止任务。

### 3.3 从一次使用到持续经营

一次任务的价值有限。Byering 的长期价值在于持续积累：

- 潜客与客户状态；
- 互动和对话证据；
- 已验证的筛选规则与回复策略；
- 触达结果和失败原因；
- Agent 任务结果、报告和文件；
- 账号级接待策略与人工交接记录。

这使产品从“一次性 AI 工具”逐步成为用户的经营操作系统。

## 4. 产品总体结构

Byering 可以从三个层面理解。

### 4.1 用户层：提出目标、授权、确认关键动作

用户的职责不是管理复杂 Agent 编排，而是做真正应该由经营者做的决策：

- 说明目标和业务边界；
- 选择账号并完成授权；
- 确认首次触达、敏感承诺或批量外部动作；
- 审核结果并决定人工跟进；
- 调整策略、知识和接待规则。

### 4.2 主控层：需求理解、任务状态和执行边界

主控层负责将自然语言或页面配置转成结构化任务，而不是直接把一句自由文本交给不受约束的 Agent 群。

主控层会完成：

1. 识别用户是咨询、看数据、做分析、找人、触达还是接待；
2. 生成目标、范围、缺失信息、风险和验收口径；
3. 判断任务是否需要账号授权、是否需要发送确认；
4. 选择执行边界：仅规划、公开分析或授权账号 Agent；
5. 创建可追踪任务、记录事件和结果快照；
6. 将真实执行结果同步到实时工作、成果中心和对话入口。

### 4.3 专业执行层：负责明确岗位，不越界执行

专业 Agent 只在自己的职责边界内工作。例如：

- 找客专员只收集授权账号中新出现的互动用户，不把互动直接包装成高意向客户；
- 客户分析员只分析明确传入的候选对象，不凭空声称发现了新客户；
- 潜客触达专员只在用户确认后调用云端抖音 RPA 发送首条私信；
- 私信客服只处理已有会话，不把“承接客服”变成陌生人主动私信；
- 金牌客服在自动回复规则之外遇到边界问题时必须停下来，交给人。

## 5. 用户可见产品模块

### 5.1 首次设置

首次进入产品，用户可以从五个高价值入口选择第一件要交给 Agent 的工作：

| 首次入口 | 用户得到的能力 |
| --- | --- |
| 抖音获客管家 | 从账号互动中持续找人、分析、首触达和后续会话承接 |
| 金牌客服 | 按业务目标自动接待新私信，边界问题转人工 |
| 直播间弹幕分析 | 监听和整理当前直播间的新弹幕、需求和问题 |
| 爆款作品分析 | 输入抖音作品链接，拆解内容、流量机制和可验证打法 |
| 电商直播间未成交客户触达 | 对直播互动用户按既定规则发起私信触达 |

需要读写抖音账号的能力会引导用户进入云端抖音环境完成登录；只分析公开作品的能力不应要求私域账号授权。

### 5.2 Agent 中心

Agent 中心是用户选择、雇佣、配置和启动专业能力的地方。它不是“技术插件列表”，而是岗位市场。

用户可以在这里：

- 查看 Agent 的业务职责、输入、输出和边界；
- 选择独立使用某项能力，或启动完整获客管家；
- 连接授权账号、填写目标和策略；
- 进入该 Agent 的真实工作台；
- 查看实时工作、成果中心、云电脑和历史结果。

### 5.3 实时工作

实时工作用于查看真实任务进展，而不是展示虚构的“AI 正在思考”。它会按任务、Agent 和账号显示：

- 当前运行状态；
- 已接收的任务和阶段；
- 已发现、已分析、已发送、等待回执等计数；
- 授权或连接异常；
- 任务暂停、恢复、重试、取消和人工交接；
- 关键结果和事件时间线。

### 5.4 成果中心与发现的人

成果中心承担经营结果的统一沉淀，主要包括：

- **潜客线索：** 已分析并进入经营漏斗的用户；
- **发现的人：** 有互动来源但尚未完成意向判断的原始用户池；
- **触达和回复：** 发送状态、平台回执、会话状态和留资情况；
- **报告与文件：** 客户分析、作品分析、直播分析等产物；
- **漏斗指标：** 获取潜客、已触达、客户回复、留资和转化。

指标必须遵守严格口径：发送请求、草稿和状态未知不能计入“已触达”。

### 5.5 成员与会话

成员页面将 Agent 当作可查看的业务角色。用户可以查看其当前状态、工作记录、相关结果、云电脑和配置入口。

对于客户会话，用户可以查看用户消息、自动回复、人工回复、接管原因和最近人工发送时间；这使“客服工作”从不可见的后台逻辑变成可运营的业务队列。

### 5.6 AI 办公室

AI 办公室提供组织状态的可视化：哪些 Agent 在工作、哪些等待授权、哪些已完成、哪些被阻塞。

办公室不应被理解为独立数据源。它读取与实时工作一致的任务事实，因此用户在办公室看到的状态应能回到同一任务、同一账号和同一结果记录。

### 5.7 记忆、策略与文件

- **记忆：** 沉淀用户偏好、业务规则、历史结果和 Agent 经验；
- **对话策略：** 维护账号级接待目标、知识、时间段、回复规则和转人工边界；
- **文件中心：** 打开任务产生的分析报告和其他交付物。

## 6. Agent 体系

### 6.1 当前真实 Agent 中心

当前 Agent 中心对新工作开放的是 **9 个已激活 Agent**。页面只会为这些 Agent 显示“雇佣并配置”或“立即使用”的真实入口；另有一个 `TikTok 获客管家` 的“即将开放”占位卡，不属于当前能力。

历史目录、未启用岗位、旧名称兼容记录不属于对外产品能力，也不应出现在销售材料、产品介绍或客户承诺中。

| 当前分类 | Agent | 执行类型 | 是否需要账号授权 | 当前职责与输出 |
| --- | --- | --- | --- | --- |
| 找人 | 抖音获客管家 | 长期账号级获客运行时 | 是 | 候选、分析、首触达、承接记录与运行摘要 |
| 找人 | 找客专员 | 授权账号互动监听 | 是 | 有来源证据的互动用户池 |
| 分析 | 客户分析员 | 候选清单分析 | 视输入来源而定 | 意向结论、理由、优先级和报告 |
| 触达 | 潜客触达专员 | 云端 RPA 首次私信 | 是，且必须确认发送 | 提交记录与最终平台回执 |
| 私信对话 | 私信客服 | 长期私信监听与规则回复 | 是 | 会话、回复、留资与人工交接 |
| 私信对话 | 金牌客服 | 目标驱动的长期私信接待 | 是 | 会话推进、回复记录、人工接管 |
| 分析 | 直播间弹幕分析 | 授权直播监听 | 是 | 弹幕问题、需求和分析结果 |
| 触达 | 电商直播间未成交客户触达 | 授权直播监听 + RPA | 是 | 对弹幕用户的触达执行记录 |
| 分析 | 爆款作品分析 | 公域作品分析 | 否，需提供完整作品链接 | 内容分析报告和创作建议 |

> 当前页面的分组为：**找人**（抖音获客管家、找客专员）、**分析**（客户分析员、直播间弹幕分析、爆款作品分析）、**触达**（潜客触达专员、电商直播间未成交客户触达）和 **私信对话**（私信客服、金牌客服）。

### 6.2 完整获客管家与单能力 Agent 的关系

“抖音获客管家”是全链路产品，不是简单父 Agent。它将账号互动监听、找人、分析、触达和承接连接为一个长期任务。

单能力 Agent 则适用于用户只想解决某一个明确问题，例如只分析一批候选用户、只做首次私信、只接待新私信或只分析作品。

为避免同一个账号出现重复回复或多套策略冲突，系统需要维持账号占用和私信承接归属：

```text
一个授权抖音账号
  -> 一个云端抖音会话（执行载体）
  -> 同时可以承载多个语义 Agent 的能力
  -> 但同一时刻只有一个私信承接器拥有该账号的会话回复权
```

## 7. 从用户目标到真实结果的通用逻辑

### 7.1 目标理解

用户可以从首页对话、首次设置、Agent 中心、成果中心或实时工作进入任务。

系统首先将输入归为以下几类：

- 咨询：解释产品能力或使用方法；
- 数据查询：读取已沉淀的 Agent 结果，例如“昨天各个 Agent 做了什么”；
- 规划：形成任务目标、范围、验收标准和风险边界，不执行外部动作；
- 公域分析：分析公开账号、评论或作品；
- 授权账号任务：读取已授权抖音账号的互动、直播或私信；
- 外部动作：首次私信、直播间即时触达、自动私信接待等。

如果信息不足，系统应提出必要澄清，而不是臆造客户、人群、账号或发送内容。

### 7.2 任务提案与确认

对于可执行任务，系统会形成结构化提案，至少明确：

- 目标和期望结果；
- 负责 Agent；
- 数据来源和范围；
- 是否需要授权账号；
- 是否会执行外部发送；
- 需要用户确认的动作；
- 风险、缺失信息和验收口径。

任务不应因为用户输入一句模糊话而直接进入外部执行。尤其涉及抖音账号、私信和长期监听时，必须先完成授权和必要配置。

### 7.3 任务状态机

每个任务具有明确生命周期，避免“页面看着在跑，实际上不知道在做什么”。

```text
CREATED
  -> WAITING_REQUIREMENT   等待用户确认目标或补齐信息
  -> WAITING_ACCESS        等待账号登录、授权或作用域确认
  -> RUNNING               正在执行
  -> WAITING_APPROVAL      等待用户批准高风险动作
  -> WAITING_REPLY         等待业务对象或用户的后续回应
  -> HANDOFF_REQUIRED      需要人工接管
  -> PAUSED / RETRYING     暂停或重试中
  -> SUCCEEDED / FAILED / CANCELLED / BLOCKED
```

状态变化通过带版本号和幂等键的命令驱动。配置更新要求携带当前版本，以避免两个页面或两个操作者互相覆盖。

### 7.4 执行边界

系统会明确选择任务的执行边界：

| 执行边界 | 用途 | 能否访问账号私域数据 | 能否对外发送 |
| --- | --- | --- | --- |
| 仅规划 | 生成策略、任务拆解、验收标准 | 否 | 否 |
| 公域发现/分析 | 公开作品、公开评论或公开账号研究 | 否 | 否 |
| 授权账号 Agent | 评论、互动、直播、私信等账号内动作 | 是，需授权 | 仅在策略和确认满足后 |

这意味着“分析公开内容”和“使用用户抖音账号执行发送”是两件不同的事，不能通过一个模糊授权混在一起。

### 7.5 事件、结果和可观测性

任务执行期间会持续记录事件，例如：

- 任务创建、配置更新、需求确认；
- 授权申请、授权成功或失效；
- 候选发现、分析完成、触达准备；
- 发送提交、平台回执、回复到达；
- 人工接管、恢复 AI、暂停、失败和重试；
- 分析报告、文件和结果快照生成。

结果不是只留在当前浏览器内。系统有按租户隔离的结果账本，保存 Agent、任务、账号、状态、结果快照和更新时间；主 Agent 可以据此回答“昨天哪些 Agent 有结果”“一共发现多少客户”等数据问题，而不是临时编造答复。

## 8. 关键业务流程

### 8.1 流程一：完整抖音获客

**适用场景：** 用户希望把某个已授权抖音账号的持续获客交给一套 Agent 完成。

```text
授权账号的新增评论 / 互动通知 / 直播弹幕
  -> 找出互动用户与原始证据
  -> 去重、补全来源与身份
  -> 依据规则判断是否值得推进
  -> 符合条件后按受控策略发起首次私信
  -> 等待真实平台回执
  -> 用户回复后进入私信承接
  -> 留资、人工接管或继续跟进
  -> 写回成果中心和结果账本
```

关键规则：

1. 只处理开启后接收到的新信号，不承诺静默回扫所有历史内容；
2. 评论、弹幕和互动是证据来源，不自动等于购买意向；
3. 相同客户的来源需要合并，不能因多条互动重复触达；
4. 用户拒绝、要求人工、投诉或策略边界只停止该客户的自动化，不应停止整个账号任务；
5. 账号级日限额、排队、失败和未知回执必须保留；
6. 同一客户首触达的提交、送达和未知状态不允许被盲目重复创建。

### 8.2 流程二：找客专员 -> 客户分析员 -> 潜客触达专员

**适用场景：** 用户希望逐步操作，而不是启动完整自动获客任务。

```text
找客专员
  -> 收集授权账号中新增互动用户
  -> 写入“发现的人”

客户分析员
  -> 接收明确选择的候选用户
  -> 分析原话、来源、需求信号与信息缺口
  -> 写入“待确认触达”或归档

潜客触达专员
  -> 用户确认目标、账号和内容
  -> 调用云端 RPA 发送首条私信
  -> 等待最终平台回执
  -> 成功后进入已触达 / 跟进中
```

这条流程的重要约束是：下游只能消费上游真实结果。潜客触达专员不能跳过找人和分析，直接把任意昵称当作可发送对象；客户分析员也不能声称候选来自一个未运行的账号监听任务。

### 8.3 流程三：金牌客服与人工接管

**适用场景：** 用户希望把授权账号的新私信交给 AI 接待，并按自定义业务目标推进，例如预约试驾、产品咨询、收集需求或预约沟通。

```text
新私信到达
  -> 读取客户历史和账号策略
  -> 判断是否允许自动回复
  -> 生成有依据的回复并再次校验
  -> 通过云端 RPA 真实发送
  -> 持久化会话、回复与发送状态
```

自动回复的前提包括：

- 账号已授权且私信监听运行；
- 已设置业务目标、知识、回复规则与转人工边界；
- 当前会话未被人工接管、未关闭、未拒绝联系；
- 回复不涉及无依据的价格、承诺、投诉处理或敏感信息；
- RPA 返回的结果未明确失败。

**转人工处理的真实语义：**

1. 用户或策略触发接管后，该客户会话持久化为 `human`；
2. AI 在生成前读取一次会话状态，生成结束、发送前再读取一次；
3. 因此即使客服在 AI 生成过程中点击“转人工”，旧回复也不会在接管后晚发；
4. 人工输入的消息通过同一授权账号的抖音云端 RPA 发送；
5. 人工发送有请求幂等保护，网络超时重试不会盲目重复发；
6. 人工消息、客户新消息、接管原因和时间都写入会话历史；
7. 用户可选择“恢复 AI 接管”，将单个会话切回 `auto`，不影响其他客户。

这不是前端把按钮文案改成“人工处理中”，而是对 AI 自动发送权的真实切换。

### 8.4 流程四：规则型私信客服

**适用场景：** 用户已有明确的账号接待策略，例如产品知识、营业时间、离线留言、价格问题是否转人工等。

私信客服按账号级策略运行。其逻辑是：

```text
收到私信
  -> 识别意图：问候、产品咨询、价格、购买意愿、投诉、拒绝等
  -> 检查会话归属、营业时间、知识完整性和策略边界
  -> 可回答：生成并发送
  -> 需要人工：停止自动化，保存上下文
  -> 用户拒绝：关闭该会话
```

该 Agent 不主动寻找陌生人，不使用主动触达接口，不将自己的出站消息再次当成用户消息处理。

### 8.5 流程五：直播间弹幕分析与即时触达

**弹幕分析：** 对已授权账号当前直播间的新弹幕进行实时收集和分析，输出客户问题、需求、商品相关信号和待处理事项。它不自动等同于触达或成交。

**未成交客户触达：** 对直播间出现的弹幕用户按用户配置的内容规则发送私信。该功能的业务设定是“弹幕出现即触达”，因此不对每一条弹幕先宣称其为高购买意向；发送频控、模板、每日上限和授权账号依然需要遵守。

### 8.6 流程六：爆款作品分析

**适用场景：** 内容创作者、运营人员或品牌主提供一条完整抖音作品链接，希望理解其为什么有效，以及哪些方法可迁移。

```text
用户提交完整作品链接
  -> 校验链接格式
  -> 获取作品详情与可用的公开信息
  -> 读取视频或关键帧、文本和可选评论
  -> 分析内容结构、受众需求、互动信号和创作机制
  -> 生成报告、证据和可执行建议
```

该能力不应伪称能获得没有开放的数据；若评论、视频帧或外部信息无法取得，报告应明确说明证据范围和缺口。

## 9. 账号授权、云端 RPA 与真实执行

### 9.1 为什么必须有云端抖音环境

抖音内的私信读取、私信发送、直播消息轮询等动作，需要在用户已登录、已授权的账号环境中执行。Byering 使用云端抖音会话作为执行载体，再由 MCP/RPA 适配层调用对应动作。

用户体验上，这意味着：

1. 用户先选择要使用的 Agent；
2. 系统启动或恢复该账号对应的云端环境；
3. 用户在云端页面完成抖音登录；
4. 系统读取账号状态并绑定确认的账号身份；
5. 之后该账号上的监听、私信发送和承接使用同一个已授权会话。

### 9.2 账号与云端会话的关系

一个真实抖音账号对应一个持久化云端会话。服务重启后，系统优先恢复已保存的远端 `session_id` 并检查登录状态，而不是不必要地重新开一台云电脑。

这带来三个好处：

- 降低重复登录和重复订阅成本；
- 减少同一账号被多条流程抢占的风险；
- 保持任务恢复时的账号身份连续性。

### 9.3 真实发送与回执口径

任何外部动作至少分为四个阶段：

| 阶段 | 含义 | 是否可计为已触达 |
| --- | --- | --- |
| 待确认 | 用户尚未批准发送 | 否 |
| 已提交 | 系统已向 RPA 发出执行请求 | 否 |
| 等待平台回执 | RPA 或平台未给出最终状态 | 否 |
| 已送达 / 已发送 | 平台或 RPA 明确回传成功 | 是 |
| 失败 / 未知 | 平台拒绝、异常或无法确认 | 否 |

因此，“点击发送成功”“接口 HTTP 200”不等于“客户已收到消息”。

### 9.4 幂等、串行与恢复

真实执行必须防止重复：

- 同一条私信请求带稳定请求 ID；
- 同一账号的关键收发动作使用账号级协调队列；
- 已提交或已送达的请求不能再次发送；
- 失败请求会记录失败状态，允许经过判断后重试；
- 任务、游标、消息去重 ID、会话状态和回执状态持久化；
- 服务重启后从持久化状态恢复，而不是从头猜测已执行过什么。

## 10. 证据、客户状态与结果口径

### 10.1 证据优先

Byering 中的判断需要区分“事实”“推断”和“未知”。

**可作为事实的例子：**

- 用户在某条作品下的原始评论；
- 当前直播间中返回的弹幕文本；
- 账号公开资料和作品信息；
- 用户在私信中明确表达的需求或联系方式；
- 云端 RPA 返回的发送成功或失败回执。

**不能直接当事实的例子：**

- 点赞等弱信号；
- 模型对购买意愿的无来源猜测；
- 未返回平台回执的发送请求；
- 账号不存在或无法读取时由模型补写的资料。

### 10.2 潜客状态

| 状态 | 含义 | 可进入的后续动作 |
| --- | --- | --- |
| 待分析 | 已发现原始互动用户，尚未判断价值 | 客户分析 |
| 待触达 | 完整获客管家的自动流程正在处理 | 查看运行进展 |
| 待确认触达 | 已分析，等待用户确认首条私信 | 选择对象和确认发送 |
| 已触达 | 有最终成功/送达回执 | 等待回复或进入接待 |
| 跟进中 | 已回复或在持续对话 | AI 或人工持续承接 |
| 已留资 | 已识别明确联系方式并保留原话 | 人工成交跟进 |
| 成交跟进 | 已进入业务人员的成交动作 | 人工业务流程 |
| 已转化 | 业务已确认成交 | 复盘、归因和复购 |
| 已失效 / 已归档 | 拒绝、无效或当前不适合推进 | 保留历史，不继续自动触达 |

### 10.3 漏斗指标

产品可以展示下面的经营漏斗，但每个数字必须来自真实状态：

```text
获取潜客
  -> 私信触达
  -> 客户回复
  -> 完成留资
  -> 业务转化
```

| 指标 | 口径 |
| --- | --- |
| 获取潜客 | 已进入潜客池的有效用户数 |
| 私信触达 | 有最终成功/送达回执的首次私信数 |
| 触达率 | 私信触达 ÷ 获取潜客 |
| 客户回复 | 已触达后收到真实回复的用户数 |
| 回复率 | 客户回复 ÷ 私信触达 |
| 完成留资 | 明确提取到手机号、微信、邮箱等且有来源证据的用户数 |
| 触达留资率 | 完成留资 ÷ 私信触达 |
| 转化率 | 已转化 ÷ 获取潜客 |

## 11. 权限、风控与人工控制

Byering 的商业价值越接近交易，越不能只靠提示词约束。系统需要同时使用产品交互、任务状态、账号作用域、策略检查和 RPA 回执来控风险。

### 11.1 权限原则

1. **最小授权：** 公域分析不应要求读取私信；私信发送不应访问未授权账号；
2. **账号隔离：** 不同账号的数据、会话和云端会话应分开；
3. **租户隔离：** 结果、任务和账号绑定按用户/租户范围读取；
4. **动作确认：** 首次私信和其他高风险外部动作要求明确确认；
5. **证据可追溯：** 每一个结论和发送状态都应有来源；
6. **失败可见：** 授权失效、模型未配置、RPA 异常、数据不足不能用成功文案掩盖；
7. **人工可夺回控制权：** 会话、任务和策略都应该允许用户暂停、取消或接管。

### 11.2 典型自动转人工条件

以下情况应默认停止 AI 自动推进：

- 客户明确要求人工、真人客服或老板；
- 投诉、退款、纠纷和高敏感问题；
- 价格承诺、优惠承诺、库存承诺等无已批准事实的问题；
- 已配置知识库无法覆盖的问题；
- 用户明确拒绝或要求勿扰；
- 会话已经被人工接管；
- 平台身份、账号归属或发送结果无法确认。

### 11.3 人工接管不是“暂停整个 Agent”

人工接管应是客户会话级能力：

```text
账号监听仍继续
其他客户仍可按规则被处理
只有当前客户会话进入 human 状态
该会话的 AI 生成与发送被停止
人工可在同一会话中用同一授权账号回复
```

这是客服业务中最重要的粒度：既保护关键客户，又不让整个账号运营停摆。

## 12. 技术与数据架构

### 12.1 前端工作台

前端主要负责：

- 目标输入和配置表单；
- Agent 广场和工作台；
- 授权流程、云端桌面和错误提示；
- 实时任务、会话和结果展示；
- 成果中心、联系人、文件和策略页面；
- 用户确认、人工接管、暂停、恢复和重试动作。

前端不应作为最终事实来源。客户、任务、发送和结果状态应由后端控制面持久化。

### 12.2 控制面

控制面是业务状态的核心，负责：

- 需求理解与任务提案；
- 任务命令校验、幂等和状态迁移；
- 账号访问确认；
- 任务事件日志和订阅；
- 结果快照与 Agent 结果账本；
- 用户、租户和账号范围隔离；
- 对核心执行服务发出受约束的运行请求。

### 12.3 核心执行服务

核心执行服务只接受明确的 Agent、任务、账号和配置，不允许一个通用入口隐式绕过产品边界。

它根据 Agent 类型调用：

- 持续获客运行时；
- 候选客户分析服务；
- 云端 RPA 私信触达；
- 私信承接运行时；
- 直播弹幕监听；
- 公域作品分析服务。

### 12.4 抖音云端执行层

抖音云端执行层由三部分构成：

```text
Byering 控制面
  -> 账号级云端会话注册表
  -> Douyin MCP 适配服务
  -> 云端浏览器 / RPA / 渠道服务
  -> 抖音账号实际读取与发送动作
```

注册表保存已验证的账号身份与远端会话标识；MCP 服务负责启动私信模式、拉取消息、读取直播消息、发送消息等动作；RPA 是对抖音平台真实界面的执行层，而不是纯本地模拟。

### 12.5 持久化对象

系统当前重点持久化以下对象：

| 对象 | 作用 |
| --- | --- |
| 任务与命令事件 | 保证任务状态、重试和事件顺序可回溯 |
| 授权账号与云端会话 | 保证账号绑定和重启恢复 |
| 账号接待策略 | 保存知识、规则、营业时间和转人工边界 |
| 客户会话 | 保存自动/人工归属、历史、接管原因和人工回复 |
| 发送投递记录 | 保障幂等、防重复发送和失败重试 |
| 潜客与结果快照 | 为成果中心、漏斗和主 Agent 数据回答提供事实来源 |
| 分析报告与文件 | 承载可查看、可交付的业务产物 |

## 13. 对外价值表达

### 13.1 面向商家的一段完整介绍

Byering 帮你把抖音里原本散落的评论、弹幕、互动和私信，变成一条可以持续经营的客户链路。它先从已授权账号的新互动中保留原话和来源，筛出值得继续处理的人；再按你的规则完成分析、首次触达和私信接待。需要发送时，它会在你的授权账号环境中真实执行并等待平台回执；遇到价格、投诉、承诺或客户要求人工时，它会停止自动回复，把完整上下文交回给你。你看到的不只是“AI 做了什么”，而是哪些客户已发现、已触达、已回复、已留资，以及下一步该由谁处理。

### 13.2 面向小团队的价值

小团队不缺零散工具，缺的是一条不会断的经营链路。Byering 将找人、判断、首次触达、客服承接和结果沉淀放在同一套账号、任务、证据和客户状态里，减少人工在多个表格、聊天窗口和工具之间来回切换。

### 13.3 面向运营负责人或合作伙伴的价值

Byering 的差异不在于“能不能生成一段文案”，而在于它把 Agent 输出接到真实执行和可审计结果上：每个账号有权限边界，每个任务有状态机，每次发送有回执口径，每条客户线索有来源证据，每次人工接管能真正阻止 AI 继续回复。

## 14. 商业化建议

> 本节是建议路线。当前代码没有固化价格、套餐或分成规则。

### 14.1 价值计费单位

推荐不要只按“聊天次数”收费。更接近用户价值的计费单位包括：

- 授权抖音账号数；
- 云端账号运行时长；
- 每月可分析互动量、候选数或作品数；
- 私信触达与自动承接额度；
- 高级分析报告和导出能力；
- 多人协作、审批、审计和 CRM/数据连接器；
- 企业级账号管理、策略模板和 SLA。

### 14.2 建议套餐结构

| 套餐方向 | 目标用户 | 核心卖点 |
| --- | --- | --- |
| Starter | 个体创作者、刚开始经营抖音的人 | 作品分析、少量候选分析、一个账号的基础接待 |
| Growth | 小商家、主播、个人 IP | 持续获客、首触达、金牌客服、成果漏斗 |
| Team | 多账号、小型销售与运营团队 | 多账号、成员协作、审批、策略模板、结果导出 |
| Enterprise | 连锁门店、品牌与专业销售组织 | 账号矩阵、权限、审计、数据接入、私有部署或 SLA |

### 14.3 关键商业原则

1. 云端 RPA 和平台执行是成本项，必须和纯分析能力分开计价；
2. 不应承诺保底成交或虚构确定收益；
3. 应用真实漏斗定义价值，不用“生成次数”掩盖无效工作；
4. 高风险发送、敏感行业和高额度执行应有更高的审核和风控等级；
5. 长期壁垒来自账号策略、客户资产、转化数据和可复用 SOP，而不是单一模型调用。

## 15. 当前成熟度与诚实边界

### 已落地且应作为当前产品能力表达的内容

- 抖音 Agent 广场、首次任务选择、Agent 工作台和实时任务视图；
- 授权账号的云端会话管理、登录恢复和账号身份绑定；
- 账号级互动监听、候选发现、客户分析、首触达和私信承接的核心链路；
- 抖音获客管家、找客专员、客户分析员、潜客触达专员、私信客服、金牌客服、直播能力和作品分析等核心执行入口；
- 任务状态机、事件记录、结果快照、成果中心和 Agent 数据汇总；
- 发送确认、账号边界、平台回执口径、幂等和错误可见性；
- 金牌客服的真实人工接管、人工回复和恢复 AI 接管；
- 文件报告、联系人/会话、办公室联动和策略配置入口。

### 需要根据客户环境确认后再承诺的内容

- 某个抖音数据接口、直播间消息或账号资料在目标账号上是否可读；
- 某个 Agent 是否已配置所需的模型、数据服务或外部连接器；
- 云端抖音环境的登录有效期、平台频控、执行速度和最终送达率；
- CRM、支付、电话、企业审批等第三方系统的具体集成；
- 所有 Agent 广场岗位在当前部署环境下是否均具备生产级执行连接器。

### 尚不应对外承诺为“已完整上线”的内容

- 任意自然语言目标都能自动调度无限数量 Agent 并自行完成所有业务；
- 无需账号授权即可读取私信、直播或执行发送；
- 未经人工确认即可无限制批量触达；
- 通过 AI 判断直接保证成交率或用户购买意图；
- 完整企业 CRM、全渠道营销和财务归因已经全部打通。

## 16. 结论

Byering 的本质是一套面向抖音经营的、以真实执行和真实结果为中心的 Agent 系统。

它的产品飞轮是：

```text
更多被授权的业务动作
  -> 更多真实互动、回复和回执
  -> 更完整的客户与结果资产
  -> 更准确的策略、优先级和人工判断
  -> 更高质量的下一轮获客与转化
```

真正的竞争力不在于展示多少 Agent，也不在于生成多少话术，而在于让用户放心把重复但关键的经营动作交出去，同时始终保留账号、策略、风险和客户关系的控制权。

**一句话总结：Byering 让抖音经营者拥有一支能找人、能判断、能执行、能接待、能交接、也能对结果负责的 AI 业务团队。**
